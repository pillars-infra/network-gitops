# Pod CIDR ownership and fabric next hops

The existing `podcidr-fabric-reconciler` remains the sole host actor for this policy. Its native release installs configuration before workloads. Both scripts are mounted from the same authenticated ConfigMap and their combined digest drives the DaemonSet rollout.

The local host ledger is `/var/lib/re8ch/podcidr-fabric/owned-prefixes.json`. It records prefixes only after native fail-fast `vtysh -c` batch execution and independent local-origin/Null0 readback (including absence of retired ownership), with the CiliumNode UID, observed resourceVersion and Kubernetes Node owner UID. The controller reads actual `spec.ipam.pools.allocated` entries, including every pool/CIDR. An explicitly present empty allocation array authorizes withdrawing previously accepted pool prefixes. Missing fields, conflicting assignments and API outages do not authorize withdrawal or overwrite the accepted ledger. Normal CiliumNode recreation on the same Kubernetes Node owner UID migrates the source UID/resourceVersion after successful application and still withdraws retired prefixes. A different Kubernetes Node owner UID fails closed; missing owner references are unknown and cannot authorize withdrawal.

For an installation without a ledger, cleanup is limited to an exact prefix assigned to another declared fabric member for which this host still has both a locally sourced BGP origin and a static distance-254 blackhole. It never removes an arbitrary static or learned route. Subsequent cleanup uses the durable ownership ledger, including prefixes no longer allocated anywhere. Inventory-declared legacy compatibility prefixes remain desired while that declaration remains in force.

Each route server rewrites admitted fabric routes to its own address on the receiving peer's actual link: identity, transport or interconnect. This avoids propagating a private transport next hop across an unrelated fabric. Provider/public peers and export filters are outside these loops.

Before execution, compare the full native cohort against actual state; do not blindly roll back unrelated live controller configuration. After execution verify the mounted script/helper hashes, actual new processes, current Cilium allocations, removal of the retired local origin/blackhole and usable forward/return routes. Check both directions of real Pod traffic and then restore DNS placement across the intended nodes. A Pod Ready flag, template digest or one successful DNS request is insufficient evidence of path stability. Any controlled Pod rebuild uses the native reviewed plan path, never SSH writes.

The RR interconnect also admits the exact observed Cilium allocations of declared non-local fabric members as WireGuard source prefixes. Rewriting BGP next hops alone is insufficient: a legal un-SNATed Pod packet forwarded through another RR must pass the receiving peer's cryptokey source check. This includes every allocation of a multi-prefix node, not just the other RR's own Pod CIDR. Existing host identities and compatibility entries are preserved; no entire pool, public peer, or default route is added. Entries owned by other configuration are not removed by this additive source reconciliation.

Spoke peers have different ownership from that aggregate interconnect. With an authoritative allocation snapshot, the controller removes an exact Pod prefix from an incorrect spoke peer before retaining/adding that peer's own prefixes. This prevents a later update of the old peer from taking WireGuard's unique per-interface prefix owner back from the new peer. The same rule applies to declared public-mesh spoke peers; it does not change public endpoints or routes. Only positively reassigned registered-member allocations are removed. Unknown snapshots, unassigned/foreign entries and explicit relay sources through the existing R640 transit remain intact. The RR interconnect retains its all-fabric source semantics and is not treated as a single spoke.
